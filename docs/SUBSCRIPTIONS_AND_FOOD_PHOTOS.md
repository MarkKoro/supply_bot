# Общий экран подписок и обычные фото Food

## Один источник кода

Core, его расчёт общей подписки и общий экран находятся только в
[MarkKoro/progressor_core main](https://github.com/MarkKoro/progressor_core).
Экран `/progressor/assets/navigation.v1.js` одинаков для всех трёх WebApps.
Боты содержат `ProgressorDomain.subscriptionPlans/purchaseSubscription` —
тонкие вызовы собственных тарифов и платёжных экранов. Не копировать Core UI
в каждый бот и не возвращать прежний Gym integrations/progressor_core.
`shared/progressor_bot.py` — канонический Telegram helper; его три зеркала
обновляются вместе с main всех трёх ботов.

## Доступ и покупка

«Подписки» открывает четыре карточки: Food, Gym Diary, Supply, Все вместе.
Карточка показывает текущий доступ, срок, отдельную/общую/пробную подписку,
бесплатный дневник или отсутствие покупки. При устаревшем снимке показывать
«Уточняем доступ», а не предлагать повторно оплатить якобы отсутствующую покупку.
Источники legacy могут не отличать подарок от отдельной подписки: честная
надпись «Отдельный доступ»; не выдумывать происхождение денег.

`GET /api/v1/me/subscriptions` выводит только собственные сведения о доступе
по проверенному Telegram subject, без данных здоровья и питания. Просмотр
статусов не зависит от готовности платёжного провайдера и не вызывает ИИ.
Пробный доступ виден, но не увеличивает права на межпродуктовые личные данные.
Подтверждённый общий период остаётся видимым при кратком отказе источника;
cross-context по устаревшим снимкам всё равно закрыт.

Для каждого доступного тарифа — пара одинаковых кнопок ₽ и Stars. Ни одному
способу не придавать визуальный приоритет. Рубли сохраняют существующий путь:
платёжный экран продукта/отдельный сайт → YooKassa Redirect confirmation_url.
Общая RUB покупка — `/progressor/subscribe?source=…&plan=…`, вход через свой
бот, повторная проверка цены на сервере, далее внешний сайт ЮKassa.
Stars — существующий invoice и проверенные precheckout/successful_payment.
Открытие/возврат с сайта не подтверждает оплату: доступ даёт только серверная
проверка провайдера. Не обходить проверку владельца, суммы, валюты и срока.

Общая цена и денежный зачёт — один расчёт Core финансовой версии2:
докупить до ближайшей текущей даты или купить новый общий период.
Подарочные/trial дни сохраняются, но не засчитываются как деньги. Резерв,
неизвестный результат провайдера и повторное событие не создают вторую оплату.
Использовать фактический order_id, возвращённый сервером, даже если он переиспользовал
существующий неоплаченный счёт. Лимиты ИИ не расширяются общей подпиской.

Food `POST /api/payments/stars/create` принимает только plan_id и проверяет
Telegram identity. Сумма/валюта/владелец выбираются сервером; callback и ledger
остаются прежними. Отдельная покупка в чужом WebApp переводит в WebApp владельца
с сохранением проверенного входа; Core не покупает отдельный тариф за другой бот.

## Food: камера → фото → результат

Основной путь — обычное фото Telegram, без выбора «Отправить файл» и без
обязательного меню уточнений. Выбирается PhotoSize с максимальным width×height,
а не последний элемент массива. Caption — необязательные сведения о порции/блюде.
Image document — дополнительный путь через тот же расчёт, не требование к пользователю.
Если анализ не удался, остаётся прежнее меню уточнения/повтора/отмены; баланс и
приём пищи не изменяются. Существующая система одного меню сохраняется.

До ИИ: ограничение Telegram getFile20MB и собственного decoded image24M pixels,
проверка формата и целостности, исправление EXIF orientation даже у маленьких фото.
Обычный подходящий JPEG сохраняется байт в байт без второго lossy encode.
Изменённая/слишком большая картинка преобразуется с сохранением пропорций, без
увеличения маленького снимка. Defaults: max side2048, JPEG quality90,
subsampling0, detail high. Входные JPEG/PNG/WEBP/nonanimated GIF; анимация и
повреждённые изображения отклоняются до запроса. Telegram уже мог сжать фото;
сервер не может восстановить детали, которых в полученном варианте нет.

Фото, текст и транскрипция голоса используют один food.composition.v2 контракт:
КБЖУ за порцию +54 nullable nutrients_per_100g. Совместимые configured модели
получают strict JSON Schema; неизвестная owner model остаётся в JSON mode.
Модели production не меняются этим выпуском. Итого за порцию пересчитывается
сервером арифметически; микронутриенты масштабируются по граммам внутри атомарного
сохранения владельца. Неизвестное не превращать в0; сохранять единицы, источник,
coverage и meal version. Это оценка состава пищи, а не анализ крови или диагноз.

Один успешный фотозапрос — один вызов AI. Единственная дополнительная попытка
допустима для malformed/schema ответа фото. HTTP/timeout/refusal/no-food/length
не запускают автоматический повтор. Text — один вызов; голос использует прежнюю
транскрипцию и этот же анализ, без отдельного запроса для нутриентов.
Owner-local AI guard/preflight и stable source_key photo:chat:message защищают
квоту, баланс и дедупликацию. Повтор доставленного фото не скачивается и не
анализируется снова; pending state очищается после обнаружения сохранённого приёма.

Ручные поля микронутриентов удалены из Food WebApp. Новый блок «Состав пищи ·
оценка ИИ» только читает сохранённые значения. Исторические ручные исправления
и совместимые backend endpoints сохранены; их нельзя удалять вместе с UI.

## Проверка и выпуск

Проверять сочетания всех8 доступов на трёх entry points, trial/common/unknown,
равные пары валют, денежный зачёт, отдельный/общий invoice и внешнюю RUB ссылку,
320/390/768px и отсутствие ручных nutrient inputs. Изолированная среда без
ключей может подставлять доступность провайдера и invoice URL только в браузере;
цены/статусы/auth остаются фактическими API тестовых аккаунтов.

Food tests: камера и optional document, EXIF/ресайз/сохранение JPEG, nullable
состав и арифметика, malformed retry, no-food/refusal/length, реальное owner
сохранение/повтор/неуспех без списания. Никогда не запускать второй consumer
или реальные платёж/AI вызовы для проверки. Физический Telegram/mobile и
accuracy benchmark на реальных снимках не заменяются браузерной эмуляцией.

Выпуск: свежий bounded backup + SHA256 + восстановление4 SQLite на временных
копиях + копия вне сервера; normal FF main4; существующий update-all;9 units,
health/readiness, source freshness, financial gate2, auth isolation и живые DB
проверяются независимо. Не менять tracked live Food SQLite файлом из Git.
Откат только к финансово совместимому коду, сохраняя все последующие user writes.
